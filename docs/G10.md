# G10 - Conversation creation and listing

Creation is exposed through `createConversation()` in
[lib/actions/conversation.ts](../lib/actions/conversation.ts).
The module has a top-level `"use server"` directive and exports only the async
creation action. The insert, validation, and sanitized storage error handling
are implemented directly in the action.

Listing is the ordinary server-only `listConversations()` function in
[lib/conversations/getter.ts](../lib/conversations/getter.ts).
Server Components import and call it directly. The reader imports `server-only`
and has no `"use server"` directive. There is no collection API route.

| Operation | Success result | Failure result |
| --- | --- | --- |
| Creation action | `ConversationMetadata` | `ChatError` with code `database` |
| Direct list reader | `{ conversations: ConversationMetadata[] }` | `ChatError` with code `database` |

Use `"error" in result` to distinguish failures. An empty collection returns
`{ conversations: [] }`. Metadata uses `Date` instances validated by `z.date()`;
`updatedAt` can also be null. React supports these values in Server Action results
and props passed from Server Components to Client Components. These are React
serialization boundaries, not JSON metadata endpoints. JSON date strings do not
satisfy this schema.

Creation takes no application input. The server supplies `New chat`; PostgreSQL
defaults generate the UUID and creation timestamp, leaving `updatedAt` null.
The action parses the returned database row directly with
`conversationMetadataSchema.parse(row)`. Listing parses the query results with
`conversationListSchema`. There is no date-conversion helper.

The list reader orders by
`coalesce(updated_at, created_at) DESC, id DESC`, matching the activity index and
giving ties a deterministic order. Database initialization remains lazy and uses
only the existing runtime client. Neither operation accesses checkpoint storage
or invokes a model.

Storage failures use the shared fixed public message; driver exceptions, SQL,
configuration values, and schema validation details are not returned.

## Request-time reads and refresh

The calling Server Component establishes the request-time boundary before invoking
the reader, for example by awaiting `connection()` from `next/server` outside any
storage error handler. Do not wrap the reader in `use cache` or globally cache its
results. Cache Components configuration remains unchanged. Adding the sidebar or
another application consumer belongs to the later UI goals.

After successful creation, the action calls `refresh()` from `next/cache` to rerun
the current route's server reads. It does not refresh after a storage failure.
Framework refresh work stays outside the storage catch block. The caller receives
the new UUID and can navigate or start streaming in the later integration goals.

## Human verification

With the existing database and runtime configuration ready, start the application
with `npm.cmd run dev`. Use a Next.js action caller to invoke
`createConversation` from `@/lib/actions/conversation`, and call
`listConversations` from a request-time Server Component or server context.
The action needs a Next.js action request context because it calls `refresh()`;
do not invoke it as an ordinary standalone TypeScript script.

1. Confirm creation returns a UUID, the title `New chat`, a valid `Date` for
   `createdAt`, and `updatedAt: null`. Confirm a subsequent listing includes
   the same UUID.
2. Inspect the result in the action caller and the props passed to Client Components:
   metadata timestamps remain `Date` instances, rather than ISO strings.
3. Create another conversation and confirm descending activity ordering. Equal
   activity timestamps sort by descending UUID. An already-empty database returns
   an empty array; do not delete existing data just to check this case.
4. With a server-rendered list connected, confirm successful creation refreshes it.
5. If storage is unavailable, confirm both boundaries return only
   `{ error: { code: "database", message: "Conversation storage is unavailable. Please try again." } }`
   and creation does not request a refresh.

The agent does not execute these verification steps, change the database schema,
or run automated tests.
